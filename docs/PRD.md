## 1. 개요

### 1.1 배경
발전/플랜트 열원설비(보일러, 열교환기, 냉각설비 등)의 고장 이력이 부서/현장별로 분산 관리되고 있어,
과거 고장 사례를 빠르게 검색하고 재발 방지 대책을 수립하는 데 어려움이 있다. 이를 해결하기 위해
설비별 고장 이력을 한 곳에 등록·검색·통계화할 수 있는 웹 기반 시스템을 구축한다.

### 1.2 목적
- 열원설비의 고장 이력을 표준화된 양식으로 등록·관리한다.
- 과거 고장 사례를 설비명, 기간, 고장분야, 키워드 등으로 빠르게 검색한다.
- 고장 통계(빈도, 분야별 분포, 다발 설비 등)를 대시보드로 시각화하여 유지보수 의사결정을 지원한다.
- 이미 현업에서 작성 중인 "고장상보" PDF/HWP 문서를 업로드하면 자동으로 항목을 추출해
  이중 입력 부담 없이 시스템에 반영한다.
- 향후 사내 O/H(오버홀) 공정관리 시스템 및 챗봇 시스템과 연동 가능한 구조로 설계한다.

### 1.3 목표 사용자
- 발전/플랜트 여러 부서 및 현장의 설비 담당자, 정비 엔지니어
- 로그인 절차 없이 사내망(인트라넷) 내에서 누구나 접근하여 등록/조회 가능

## 2. 범위

### 2.1 1차 범위 (In Scope)
| 영역 | 내용 |
|---|---|
| 고장 이력 CRUD | 고장 이력 등록, 수정, 삭제(또는 비활성화), 상세조회 |
| 검색/필터링 | 설비명·기기명, 기간, 지사/열공급시설, 고장분야, 상태, 키워드(자유텍스트) 조합 검색 |
| 첨부파일 | 고장 관련 엑셀·한글(HWP)·PDF 문서 업로드/다운로드 |
| 문서 자동분석 업로드 | 고장상보 PDF/HWP 개별 자동추출(상시) + 여러 건 동시 업로드(다중 파일, 상시) |
| 통계/대시보드 | 설비별 고장건수, 기간별 추이, 고장분야별 비율, 다발 설비 Top N |
| 설비 간이 목록 | 설비명/코드/위치를 간단히 등록·선택할 수 있는 최소 마스터 (상세는 향후 연동) |

### 2.2 1차 범위 제외 (Out of Scope, 추후 검토)
- 계정 로그인 및 부서별 권한 분리 (현재는 로그인 없이 운영, 추후 필요 시 추가)
- 설비 마스터의 상세 스펙 관리 (사양, 도면, 정비이력 등) — O/H 공정관리 시스템과 연동 예정
- 챗봇 연동 (사내 챗봇 팀과 별도 연동 예정)
- 모바일 전용 앱 (1차는 반응형 웹으로 커버)
- 알림/메일 발송, 승인 워크플로우

## 3. 핵심 기능 요구사항

### 3.1 고장 이력 등록/수정
- 신규 고장 이력 등록 폼 제공
- 필수/선택 입력값 구분 (아래 4장 데이터 모델 참고)
- 등록 후에도 수정 가능 (수정 이력은 최소한 수정일시만 기록, 상세 변경이력 추적은 1차 범위 제외)
- 삭제는 실수 방지를 위해 소프트 삭제(비활성화) 권장

### 3.2 검색/필터링
- 목록 화면에서 다음 조건 조합 검색 가능
  - 설비명/기기명 (자동완성 또는 드롭다운)
  - 지사 (예: 청주, 화성, 동탄, 대구, 수원 등 19개 지사)
  - 열공급시설 (지사 하위, 예: 청주열공급시설, 화성열공급시설 등 18개)
  - 발생기간 (From~To)
  - 고장분야 (기계 / 제어 / 전산 / 전기 / 인적실수 / 기타)
  - 상태 (조치완료 / 조치중)
  - 자유 키워드 검색 (고장제목, 상황, 원인, 복구내용 전문검색)
- 검색 결과 목록은 정렬(발생일시 최신순 기본) 및 페이지네이션 지원
- 검색 결과를 엑셀(CSV) 내보내기 지원 (현장에서 보고서 활용 목적)

> 지사/열공급시설/고장분야 값은 실제 운영 중인 "2020~고장상보 overview" 이력 데이터를 기준으로
> 확인한 값이며(4.4 코드 테이블 참고), 신규 지사/시설 추가 시 코드 테이블에 반영하는 방식으로 관리한다.

### 3.3 통계/대시보드
- 설비별 고장 발생 건수 랭킹 (Top N, 다발 설비 식별)
- 월별/연도별 고장 발생 추이 그래프
- 고장분야별 비율 (기계/제어/전산/전기/인적실수/기타, 파이차트 등)
- 지사별/열공급시설별 비교
- 조치완료 vs 조치중 현황 (미조치 건 알림용)
- (선택) MTBF(평균고장간격), 평균 복구시간(다운타임) 통계

### 3.4 첨부파일 관리
- 고장 이력 건당 여러 개의 첨부파일 등록 가능
- 허용 파일 형식: 엑셀(.xlsx, .xls), 한글(.hwp, .hwpx), PDF(.pdf)
- 목록/상세 화면에서 파일 아이콘(엑셀/한글/PDF 구분)으로 확인, 다운로드 지원
- 업로드 용량 제한 정책 필요 (비기능 요구사항 참고)

### 3.5 설비 간이 목록 (Equipment Lite)
- 설비명, 설비코드(선택), 사업소/현장, 설비유형 정도의 최소 정보만 관리
- 고장 이력 등록 시 이 목록에서 선택하거나 신규 설비를 즉석 등록 가능
- 향후 O/H 공정관리 시스템이 설비 마스터의 정본(SoT)이 되면, 해당 시스템과 API/DB 연동으로
  설비 정보를 동기화하는 것을 전제로 설계 (5장 향후 연동 참고)

### 3.6 문서 자동분석 업로드 (핵심 기능)

현업에서 이미 사용 중인 "고장상보" 표준 양식(PDF/HWP)과 과거 이력 엑셀을 그대로 활용해,
재입력 없이 시스템에 반영하는 것을 목표로 한다. 두 가지 하위 기능으로 구성된다.

#### 3.6.1 기능 A — 개별 고장상보 자동추출 (상시 사용)
- 사용자가 신규 고장 발생 시 작성한 **고장상보 PDF 또는 HWP 1건**을 업로드
- 시스템이 표준 표 양식을 인식하여 아래 항목을 자동 추출 (4.1 데이터 모델의 필드에 매핑)
  - 발생일시, 지사/설비명, 기기명(고장위치)
  - 공급중단 현황 (APT 세대수, 건물 개소, 중단시간, 기간)
  - 고장원인 담당자/책임자 (부서, 이름)
  - 상황(운전자/목격자 진술), 보안·경보장치 동작상태
  - 원인(4M+1분석)
  - 장애현황 (고장지장열(전력)량, 고장 지장 기간, 응급처리)
  - 복구일시, 복구내용, 재발방지대책
- 추출 결과는 **등록 폼에 자동으로 미리 채워지며, 사용자가 검토·수정한 뒤 저장**하는 방식으로 동작
  (자동 저장 아님 — 파싱 오류로 인한 오등록 방지)
- 원본 업로드 파일(PDF/HWP)은 첨부파일로 함께 보관되어 상세화면에서 원문 대조 가능
- 표준 양식이 아니거나 항목을 인식하지 못한 경우, 해당 필드는 비워두고 사용자가 수동 입력하도록 안내
  (전체 실패 처리하지 않고 부분 추출 결과라도 제공)

#### 3.6.2 기능 B — 고장상보 PDF/HWP 다중(일괄) 업로드 (상시 사용)
- 여러 건의 고장상보 PDF/HWP 파일을 한 번에 선택하거나 드래그하여 업로드
- 파일마다 기능 A와 동일한 규칙 파싱을 각각 수행하여, **파일 1건 = 고장이력 1건**으로 자동 등록
  (건별 검토 없이 바로 저장 — 다건을 빠르게 적재하는 것이 목적이므로 기능 A의 "검토 후 저장"과
  달리 즉시 등록하고, 파일별 결과를 목록으로 보여줌)
- 업로드 직후 파일별로 처리 상태(등록됨/실패)와 추출된 핵심 항목(지사·설비명·발생일시)을
  요약 표로 보여줘 결과를 바로 확인 가능
- 등록된 각 건의 출처(source)는 "parsed"로 구분 저장하여, 수동 입력·엑셀 이관 데이터와 구분

> (변경 이력) 최초에는 과거 엑셀 이력 전체를 한 번에 옮기는 "엑셀 일괄 마이그레이션" 기능으로
> 설계했고 실제 샘플 데이터로 구현·검증까지 완료했으나, 현업에서는 개별 고장상보 PDF 단위로
> 다건을 한 번에 올리는 방식이 더 실용적이라는 판단에 따라 위 방식으로 대체했다.

#### 3.6.3 파싱 방식 (제안)
- 고장상보 양식이 거의 항상 동일한 표 구조를 유지하므로, 1차는 **표(테이블) 좌표/라벨 기반 규칙
  파싱**(예: PDF 텍스트 레이어 파싱 + 라벨 매칭)으로 구현하여 속도와 비용 효율을 확보
- 규칙 파싱으로 인식이 애매한 자유서술 항목(상황, 원인, 복구내용 등)은 필요 시 LLM 보조 추출을
  단계적으로 도입 가능하도록 확장 여지를 둠 (1차 범위는 규칙 기반으로 한정)
- HWP 파일은 PDF 대비 텍스트 추출 라이브러리 선택지가 제한적이므로 별도 검증 필요 (7장 참고)

## 5. 향후 연동 계획

- **O/H(오버홀) 공정관리 시스템**: 현재 별도 팀이 구축 중. 향후 설비 마스터의 정본 데이터를
  이 시스템에서 제공받아 `Equipment.external_ref_id` 기준으로 동기화하는 것을 전제로 설계.
  1차 개발 시에는 자체 간이 설비목록으로 운영하되, 연동 인터페이스(API/DB 뷰 등)를 확장 가능한
  구조로 남겨둔다.
- **사내 챗봇 시스템**: 향후 고장 이력 검색을 챗봇 인터페이스로도 제공할 가능성 있음.
  이를 대비해 검색 기능은 별도 API(백엔드)로 분리하여, 프론트엔드 외 다른 클라이언트(챗봇 등)에서도
  재사용 가능하도록 구성.

| 일괄 업로드 안정성 | 다중 PDF 업로드 시 파일 하나가 실패해도 나머지 파일 처리에 영향 없이 독립적으로 진행, 파일별 성공/실패 결과를 제공 |

## 7. 기술 스택 (제안)

Stitch로 화면 목업을 만든 뒤 실제 기능을 연결하는 흐름을 고려하여 아래 스택을 제안합니다.

| 영역 | 제안 |
|---|---|
| 프론트엔드 | Next.js (React) + TypeScript, Tailwind CSS |
| 백엔드 | Next.js API Routes 또는 별도 Node.js(Express/Nest) API 서버 |
| 데이터베이스 | PostgreSQL (또는 사내 표준 DB가 있다면 그에 맞춤, 예: MySQL/MSSQL) |
| 파일 저장 | 서버 로컬 스토리지 또는 사내 파일서버 (인트라넷 환경 고려) |
| 배포 | 사내 Windows/Linux 서버에 Docker 또는 PM2로 구동 |
| 문서 파싱 (PDF) | pdf-parse / pdfplumber 등으로 텍스트·표 좌표 추출 후 라벨 기반 규칙 매핑 |
| 문서 파싱 (HWP) | hwp.js, pyhwp 등 HWP 텍스트 추출 라이브러리 검증 필요 (선택지가 제한적이라 PoC 우선 권장) |
| 엑셀 파싱 | openpyxl(Python) 또는 SheetJS(Node) 로 컬럼 매핑 후 일괄 등록 |

> 이 스택은 제안이며, 사내 표준 기술(예: 이미 사용 중인 DB, 서버 환경)이 있다면 그에 맞게 조정 필요.
